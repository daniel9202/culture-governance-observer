# 欄位契約變更：政見履行追蹤（`pledge_fulfillment.csv`）

資料端提出，依 `AGENTS.md`「資料端新增、改名或刪除欄位前，要先列出來，等設計端確認」。
**設計端確認後資料端才動 CSV 與 `build_data.py`。**

---

## 一、新增兩欄

### 1. `pledge_nature`（政見內容類型）

描述**政見原文本身**的性質，不是查核結果。

| 允許值 | 說明 |
|---|---|
| `具體措施` | 政見寫出可驗證的作為，例如「4 年內文化局預算增至總預算 4%」「舉辦台北國際潮流音樂節」 |
| `政策方向` | 政見只敘述方向，沒有可驗證的作為，例如張善政「桃園更好玩」 |

**為什麼要這欄**：現在無法分辨「這條政見本來就沒寫具體作為」和「這條政見有作為但我們查不到進度」。兩者在前台都只能顯示成同一種狀態，讀者會以為是候選人沒做到。

命名沿用 `candidates.csv` 既有的 `content_nature` 風格。

### 2. `related_records`（關聯施政紀錄）

指向 `candidates.csv` 裡經人工確認相關的「現任首長施政」紀錄 `id`，多筆以 `|` 分隔，選填。

分隔符沿用 `candidates.csv` 的 `related_sources`。

**為什麼要這欄**：讓前台能把「2022 年承諾什麼」和「任內做了什麼」擺在一起。目前這兩種資料分在兩個檔案、前台分在兩個區塊，同一個人會在頁面上出現兩次，無法對照。

## 二、`status` 新增一個值

現有五個值，全部保留：

```
fulfilled              已實現
partial                部分實現
in_progress            執行中
no_verified_progress   未找到可驗證進度
not_assessable         不適合評估
```

**新增**：

```
not_checked            尚未查核
```

**`not_checked` 與 `not_assessable` 的差別**，這是目前資料出錯的根源：

- `not_checked`：**本站還沒查**。不代表任何關於候選人的判斷。
- `not_assessable`：**查過了，但這條政見的性質無法評估**，例如只寫方向、沒有可驗證的作為。

目前新增的六位首長政見有多筆實際是「還沒查」，卻被標成 `not_assessable`，因為枚舉裡沒有可選的值。加了之後要逐筆改回來。

另外：**政見沒寫數量或期限，不等於無法評估**。仍然可以查有沒有啟動、進行到哪，只是未必能判定是否完全實現——那種情況該用 `in_progress` 或 `no_verified_progress`，不是 `not_assessable`。

## 三、對前台的影響（設計端要確認的部分）

1. **`fulfillment.js` 的 `statusLabels` 要加 `not_checked`**，中文標籤建議「尚未查核」。
2. **統計數字要分開算**。目前頁面把政見總數稱為「已查核紀錄」，加入尚未查核的資料後這個說法不成立。建議改成「收錄政見 N 筆，其中已完成查核 M 筆」。
3. **空狀態文案**目前寫成「完成查核後才公開」，與尚未查核的資料並存會矛盾。
4. **`pledge_nature` 怎麼呈現**：建議在政見卡上標示，讓讀者知道「政策方向」這類政見本來就難以查核，不是候選人沒做。
5. **`related_records` 怎麼呈現**：建議在政見卡下方連到對應的施政卡，或直接並列。

## 五、另外兩件，一併請設計端表示意見

### 1. `responsibility`（權責機關）目前無法彙整

13 筆有 11 種寫法：「臺北市政府文化局及所屬機關」「臺北市政府文化局及相關局處」「臺北市政府文化局、產業發展局及相關基金」⋯⋯

要定一套寫法（例如只填主責局處、相關局處另記），還是接受它只是說明文字、前台不做篩選？

### 2. 公報與新聞的權威性不同，前台沒有區分

`pledge_source_type` 已經分了「選舉公報」8 筆、「競選新聞」5 筆。公報是候選人自己向中選會登記的文字，新聞是記者整理的版本。拿新聞版本當承諾基準去查核，對候選人不盡公平。

建議前台在政見卡標示來源類型，或至少在頁面說明區講清楚兩種來源的差別。這不需要新欄位，欄位已經有了。

## 六、前台既有問題，與欄位契約無關但要一起修

資料端已回報過，都是從程式碼讀出來的：

- **縣市篩選沒有套用到首長施政區**，選了縣市仍會看到其他縣市的施政
- **`fulfillment.js` 的 `isMayorRecord` 只取 `office === '縣市長'`**，兩筆 `縣轄市長`（屏東市長周佳琪、宜蘭市長陳美玲）因此落到議員分頁，而 `councilPerson` 把頭銜寫死成「${city}議員參選人」，於是顯示成「屏東縣議員參選人周佳琪」
- **首長人物標頭寫死「現任○○長，2026 參選連任」**。魏嘉賢是前花蓮市長參選花蓮縣長，不是現任縣市長，套用會是錯的。頭銜應該來自資料欄位，不是版型

## 七、另一個檔案的待修項：假的政策論述

這件與履行追蹤無關，但同屬前台，一併處理比較省事。

`build_data.py` 原本會在輸出前把空的 `policy_argument` 填成「以{topics}為主要政策方向。」——那是用主題標籤拼出來的句子，不是候選人說的話。全庫 270 列有 135 列是這樣，其中本屆競選政見 105 筆，等於過半政見的「政策論述」欄是假的。資料端已於 commit `79003ed` 改掉，現在空就是空。

**但前台還有第二層 fallback**：

```js
// public-candidates.js 第 17 行與第 62 行
policy_argument: record.policy_argument || record.summary || ''
group.policy_arguments.push(record.policy_argument || record.summary)
```

所以那 135 筆現在顯示的是**摘要被當成政策論述**。把這兩處的 `|| record.summary` 拿掉，已經寫好的空狀態文案「尚未收錄可核實的政策論述。」就會生效。

`map.js` 第 334 行用 `item.summary || item.policy_arguments[0]`，`summary` 在先，不受影響。
